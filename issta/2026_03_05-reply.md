[A,B] Existing use cases/detection
Our tool complements rug pull detection but is not aimed at detecting rugpulls.
Its purpose is instead to enrich information on detected rugpulls by discovering examples of role-attributed transaction sequences through which rug pulls may be actuated (e.g. Motivating Example of balance manipulation, where "Contract Owner calls _mints()" after the 5-transaction initialization sequence).
Existing tools detect rug pulls without providing examples (transaction sequences) of the mechanics being used.
Pied-Piper  (Ma et al., ACM TOSEM, 2023), Tokeer (Zhou et al., ICSE-SEIP, 2024) and CRPWarner (Lin et al., IEEE TSE, 2024) either provide high-level classification labels or identify suspicious code-level features, but do not provide concrete examples of usage.
Indeed, our transaction sequence-level examples revealed 105 misclassifications in the original dataset that would be difficult to detect with only labels.
We will further clarify this in the paper.

We additionally ran our tool on 443 popular ERC-20 contracts. These had less goal violations (1.83/contract vs 2.06/contract) and vastly different goal violation distributions (only 7.8% were liquidity violations vs 47.0% in the rug pull dataset).

[B,C] False Positives
As all fuzzing is done on a testnet with the contracts deployed, there are no false positives for goal violations themselves.
However, not all goal violations detected may correspond to rug pull mechanics.
We detail the trouble making this classification in "Unclear classification of rug pulls based solely on features" of Section 7.
We will add an analysis of clearly non-suspicious goal violations to the paper, but note that the vast majority during manual inspection were suspicious.

[A] Did tool always outperform ablations?
Yes, although the performance is comparable on the Min Token Supply goal (40 seconds vs 79 seconds ablated, both versions detecting 982 violations).

[B] State Initialization details
The number of users depends on how many hardcoded addressses there are. We default to 3 users (72.1% of contracts), with the maximum being 12 users (only 3 contracts). Second most common was 5 users (12.2% of contracts).

Any Liquidity states that at least one user (e.g. an administrator) should be able to transfer their owned tokens to any other user. While in a non rug-pull setting, one would typically assume that all users can transfer their funds freely, there is a common rug pull pattern (sale-restrict) that stops non-authorized users from sending (selling) their tokens to an exchange.

[C] Design of roles/goals
The roles are based on common ERC-20 administrative patterns (Ivanov et al, ICICS 2021).
The tension is between generality (all ERC-20 tokens) and specificity (handcrafted roles/goals for specific contracts, e.g. liquidity pool vs minter vs pauser etc).
For Token Holder goals, Max Owned Token directly encodes profit-maximization intent, Min Token Supply indirectly encodes profit-maximization (assumption that rarity of tokens increases individual token value) and Liquidity encodes ownership-expectation.
For Contract Owner, Max Token Supply encodes profit-maximization at project level (assumption that more tokens leads to more project value).
Additional to the provided intuition, the Token Supply goals are further justified as they bias the solver to seek for common patterns (e.g. token destruction, arbitrary mint).
Regarding sufficiency, we note that while the RQ2 results are promising, the dataset is heavily biased towards Liquidity goal violations.
